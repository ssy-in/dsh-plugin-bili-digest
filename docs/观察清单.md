## #1 长视频的 @ 门（pending，观察 2–3 天）

- 现象（2026-10-27）：一整天 23 轮，@ 用了 3/5，**全部落在短视频赛道（短 3/3 用完），长视频 0/2 一条没推出去**。
- 初判原因：`pushTasteBar = 0.35`（`lib/core/config.js`）——长视频要过口味分门槛才推，短视频走的是另一套话术/门槛。
- 待确认（看数据，不是看感觉）：
  1. 长视频候选里，`scoreTags(meta.tags).score` 的分布到底落在哪（是不是普遍 0.1–0.3 区间）；
  2. 是门槛太高，还是长视频本身标签就对不上口味（首页推荐的长视频多是游戏/影视剪辑）；
  3. 若确实是门槛问题，候选方案：`0.35 → 0.25`，或对「标签命中任一高权重词（≥0.5）」直接放行。
- 怎么查：
  - `GET <当前 GUI 端口>/bili-digest/api/state` → `push.longLeft / longLimit / shortLeft / today`、`tagBook.taste`；
  - 日报里长视频条数 vs 实际 @ 条数；
  - 需要逐条看分数时，临时写 `.tmp-home/audit-taste.mjs`（读 `cache/feed.json` 队列 + `scoreTags` 打印分布）。

## #5 登录态两天后就死了（已定位，等新 SESSDATA）

- 现象（2026-10-29 05:00 查）：@ 停在 10-27 19:20，之后两天 0 条。`GET /x/web-interface/nav` → `code -101`，插件 `state.login.isLogin=false`；直接调 `POST /bili-digest/api/push` 返回 `{"ok":false,"error":"收藏失败：-101 账号未登录"}`（这次探测没发出任何评论）。
- 证据链：日报里「需要登录态才能看到字幕清单」的条数 —— 10-27 有 5 条、10-28 有 **32 条**、10-29 有 5 条 ⇒ 登录态是 10-27 晚上死的，之后读字幕全走 needs-login、写操作全被拒。
- 待办（等人类给新 SESSDATA）：
  1. 更新 SESSDATA 后立刻手动跑一轮，验证 @ 能不能发出去；
  2. **加保护**：`runAutoRound` 开头先 `api.me()`，`isLogin === false` 时**不尝试 @**（现在会白跑一轮、还照记收藏失败），并在当天日记/日报最上面写一行「登录态失效，去更新 SESSDATA」，`state` 里也要能一眼看到；
  3. 观察这次登录态能活多久（上次约 1.5 天），失效前是否在浏览器里开过 B 站、是否换过设备。

## #6 `cookieOf()` 没带 `bili_jct`（待验证）

- `lib/core/write.js` 的 `cookieOf()` 只发 `SESSDATA` + `buvid3`，写操作靠 body 里的 `csrf` 字段。
- 10-26/27 的 @ 是成功的，说明当时这样能用；但 B 站 CSRF 校验传统上是「cookie 里的 `bili_jct` 与表单 `csrf` 比对」，缺 cookie 有被拒风险。等新 cookie 到位后，带/不带 `bili_jct` 各试一次收藏来确认。

## 每天花 30 秒看一眼的指标

| 指标 | 看哪 | 健康区间 |
| --- | --- | --- |
| 今天读了几条 | `2026MMDD_日记.md` 里 `### ` 的条数 | 10–30 |
| 丢弃比例 | 日报末尾「被丢弃」条数 / 候选数 | 别一路全是 no-subtitle |
| @ 用了多少 | `state.push.today` / `perDay` | 别长期 0（说明门太紧） |
| 请求预算 | `state.budget.used` / 120 | 常态个位数到十几 |
| 心情档分布 | 日记里的「困困鲸此刻」 | 别整天 delighted 或整天 grumpy |
| 消息回复 | `对话.md` | 有问必答、不乱刷 |
